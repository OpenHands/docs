## Overview

Organizations in OpenHands support three roles, each with different levels of access and capabilities:
**Member**, **Admin**, and **Owner**. This page describes what each role can do.

## Role Descriptions

### Member

Members are the default role for users joining an organization. Members can:

- **Create conversations** - Start new conversations using the organization's shared credits.
- **Manage their own private settings** - Configure settings that are only visible to them, including:
  - MCP servers
  - Secrets
  - API keys
  - Git user settings
  - Slack integration

Members cannot invite new users, modify organization-wide settings (like LLM settings), or manage other users' roles.

### Admin

Admins have all the capabilities of Members, plus the ability to manage the organization's settings and users. Admins can:

- Everything a Member can do.
- **Invite users** - Send invitations to new team members.
- **Change user roles** - Promote Members to Admin or demote Admins to Members.
- **Add credits** - Purchase and add credits to the organization's shared pool.
- **Modify LLM settings** - Configure the default LLM provider and model for the organization.

Admins cannot delete the organization or claim Git organizations.

### Owner

Owners have full control over the organization. Owners can:

- Everything an Admin can do.
- **Delete the organization** - Permanently remove the organization and all associated data.
- **Claim Git organizations** - Link specific Git organizations to route OpenHands resolver requests to this organization.

<Note>
  Every organization must have at least one Owner. If you need to transfer ownership, first promote another
  user to Owner before changing your own role.
</Note>

## Conversation Usage Access

Requires a build or release containing [enterprise#1354](https://github.com/OpenHands/enterprise/pull/1354).

### Default Access

Owners and Admins can already list conversations in their organization, including conversations created by other users. They can see titles, tags, creators, status, and the total cost and token usage for each conversation. Organization reports also show aggregate usage across conversations.

This access is available with detailed usage turned off. Members retain access to their own conversations under the existing rules, but do not receive organization-wide reporting access.

### Detailed Usage

Use detailed usage to see how the cost and tokens inside a conversation are split across the main agent, sub-agent tasks and condenser, together with recorded models and task timing. This helps identify which parts of a run account for its usage.

For an Owner or Admin viewing organization conversations:

| Information | Default | Detailed usage enabled |
|---|---|---|
| Conversation list, including other users' conversations | Available | Available |
| Titles, tags, creators and conversation status | Available | Available |
| Total cost and token usage per conversation | Available | Available |
| Cost and tokens broken down by agent, task and condenser inside a conversation | Not provided by existing organization reports | Available when recorded |
| Models and task timing within that breakdown | Not provided by existing organization reports | Available when recorded |

The detailed view is off by default for both new and existing organizations. Enabling it makes the extra detail available to the organization's Owners and Admins. Members and service accounts do not gain this access.

The new endpoint is read-only and returns usage data without exposing prompts, messages, task descriptions or tool inputs and outputs. Titles and tags remain available from the existing conversation list. Missing history can leave the breakdown incomplete; the response identifies partial or unavailable data.

This does not create a new user role or a monitoring-only API key. Owners and Admins keep their existing permissions.

### Enable or Disable Detailed Usage

As an Owner or Admin, set `enable_conversation_usage_detail` to `true` through the organization settings API. Both roles already have permission to edit organization settings; an Admin does not need separate Owner approval.

Set it to `false` to disable the detailed view on the next request. Existing conversation lists and total-usage reports remain available. The setting applies to one organization.

There is no UI switch or Helm setting. See the [API overview and reference](/openhands/usage/cloud/cloud-api) for authentication and request examples.

## Private Settings

Regardless of role, all organization members have control over their own **private settings**. These settings
are personal to each user and are not visible to other organization members, including Admins and Owners.

Private settings include:

- **MCP Servers** - Configure Model Context Protocol servers.
- **Secrets** - Store sensitive values like API tokens and credentials.
- **API Keys** - Manage keys for programmatic access to OpenHands.
- **Git Settings** - Configure personal Git authentication and preferences.
- **Slack Integration** - Connect your personal Slack workspace.
