---
title: Organization Secrets
description: Share credentials with members of an OpenHands Enterprise organization.
---

Organization secrets let an Admin or Owner save a shared credential once so members can use it in
their conversations and automations. For example, a team can share a service account API token
without asking every member to enter a separate copy.

This guide covers organization-shared secrets in OpenHands Enterprise. For personal secrets and
general usage, see [Secrets Management](/openhands/usage/settings/secrets-settings).

## Scope and Permissions

An organization secret belongs to one OpenHands organization. It is available to that organization's
members, including new members, and is not automatically shared with other organizations on the same
Enterprise instance. A personal secret is private to its creator within the selected organization.

| Action | Member | Admin or Owner |
| --- | :---: | :---: |
| List secret names and descriptions | Yes | Yes |
| Use shared secrets in conversations and automations | Yes | Yes |
| Create, edit, or delete shared secrets | No | Yes |
| Read saved values in settings or the management API | No | No |

Saved values are encrypted at rest. The settings page and management API return names and
descriptions, not saved values, including to the person who created the secret.

<Warning>
  Shared secrets are delivered to members' agent runtimes so their tools can use them. Hiding saved
  values in settings does not prevent code running in those runtimes from accessing the credentials.
  Share credentials intended for use by every member of the organization.
</Warning>

## Create an Organization Secret

1. Select the organization that should own the secret.
2. As an Admin or Owner, open `Settings > Secrets`.
3. Select `Add a new secret`.
4. Enter a name, value, and optional description. Use an environment variable name such as
   `TEAM_SERVICE_TOKEN`.
5. Check `Share with organization`.
6. Select `Add secret`.

The secret appears under `Organization secrets`. Members can see its name and description and use
it in new conversations. Members cannot edit or delete it. Leave `Share with organization` unchecked
when creating a personal secret.

## Use Shared Secrets

Shared secrets are loaded alongside the user's personal secrets for the conversation's organization
and made available as environment variables. Tools can read `TEAM_SERVICE_TOKEN` from the environment
without putting its value in a prompt.

Automations can use shared secrets from their organization. They still
[run as their creating user](/enterprise/automations#automations-run-as-the-creating-user); adding a
shared credential does not change the automation's run identity.

Use distinct names for personal and shared secrets. If both have the same name, the personal secret
keeps the original environment variable name and the shared secret receives an available suffix,
such as `TEAM_SERVICE_TOKEN_2`. Avoid relying on a suffixed name that can differ between members.

## Edit, Rotate, or Delete a Secret

Admins and Owners can edit a shared secret's name and description or delete it from
`Settings > Secrets`. The edit form does not replace its value.

To replace a value through the UI, delete the shared secret and create it again with the new value.
The secret is unavailable between those steps. Releases that include the dedicated organization
secret value-replacement API can replace the stored value without deleting the secret:

1. Read `GET /api/organizations/{org_id}/secrets/{secret_name}/version`.
2. Send `PUT /api/organizations/{org_id}/secrets/{secret_name}/value` with the new `value`, the returned
   `version` as `expected_version`, and a fresh UUID as `request_id`.

Value replacement requires Admin or Owner permissions. If a response is lost, retry the identical
request. A `409` means the operation conflicts with the current state; reconcile before attempting
another replacement.

Start new conversations after changing a secret. Running conversations may retain previously
delivered values. Replacing or deleting a stored secret does not revoke the credential at its
external provider or erase copies already delivered to a runtime.
