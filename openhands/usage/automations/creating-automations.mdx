Create automations the same way in Agent Canvas, OpenHands Cloud, and OpenHands Enterprise. Review an automation
in the setup form, or ask the agent in a regular conversation and confirm in chat.

## Choose a Starting Point

<Tabs>
  <Tab title="Template">
    Templates are pre-built automations for common workflows, such as reviewing pull requests or monitoring a Slack
    channel.

    1. Open **Automate** and go to **Templates**.
    2. Pick a template and fill in its fields, such as the repository to watch.
    3. Review the automation and create it.

    Some templates finish their setup in a conversation. They open the setup view with the template's instructions
    as the first message. See [Pre-built Automations](/openhands/usage/agent-canvas/prebuilt-automations) for the
    available templates.
  </Tab>
  <Tab title="Automation Mode">
    Use the automation toggle in the Agent Canvas chat to tell the agent that you want an automation.

    1. On the home screen, switch the chat to automation mode.
    2. Describe what the automation should do and when it should run.
    3. The agent fills in the setup form. Review the fields it filled and create the automation.
  </Tab>
  <Tab title="Setup Form">
    Fill in the setup form yourself when you know what you want.

    1. Open **Automate** and add an automation.
    2. Set the name, prompt, trigger, model, repositories, and plugins.
    3. Test the automation, then create it.

    A conversation stays open beside the form. Ask the agent to fill in or change any field at any time.
  </Tab>
  <Tab title="Conversation">
    Ask the agent to create an automation in any conversation:

    ```
    Create an automation that runs every Monday at 9 AM and summarizes
    our open GitHub issues, then posts the summary to #engineering on Slack.
    ```

    The agent asks for anything it's missing, such as a repository or a Slack channel, then summarizes the
    automation and asks you to confirm before it creates it.
  </Tab>
</Tabs>

## Use the Setup Form

The setup form holds every setting of an automation:

- **Name**: A short name. The agent can suggest one.
- **Prompt**: The instructions that the agent runs on each run.
- **Trigger**: A schedule, or an event from a connected source. Event sources come from the integrations and custom
  webhooks that your backend delivers. See [Event-Based Automations](/openhands/usage/automations/event-automations).
- **Model or Agent Profile**: The model or [Agent Profile](/openhands/usage/agent-canvas/agent-profiles) that runs the
  automation.
- **Repositories**: Repositories to clone before the run starts. Their repository skills load automatically.
- **Plugins**: Plugins that add skills, MCP servers, and commands to the agent. Browse the
  [OpenHands extensions repository](https://github.com/OpenHands/extensions) for available plugins.

When the agent fills a field, the field shows a **✦** marker. Editing the field yourself clears the marker, so you
can see what you changed. The agent proposes settings in the form. It doesn't create the automation while you're in
the setup view.

The setup view is a draft until you create the automation. Drafts persist across reloads. Reopen a draft from
**Automate** to continue, and test it before you create it. When the form looks right, create the automation. It
starts enabled.

For the full setup view reference, see
[Create an Automation With the Setup Assistant](/openhands/usage/agent-canvas/managing-automations#create-an-automation-with-the-setup-assistant).

## Choose a Prompt, Plugins, or a Script

<Tabs>
  <Tab title="Prompt">
    Most automations run a prompt. Describe the task in natural language:

    ```
    Create an automation called "Daily Standup Summary" that runs every weekday
    at 9 AM Eastern. It should check our GitHub repo for PRs merged yesterday
    and post a summary to #engineering on Slack.
    ```

    A prompt is enough for reports, monitoring, data syncs, and most common tasks.
  </Tab>
  <Tab title="Prompt With Plugins">
    Add one or more plugins when the agent needs specialized skills or tools:

    ```
    Create an automation using the code-review plugin that runs every weekday
    at 9 AM. It should review any Python files changed in the last 24 hours.
    ```
  </Tab>
  <Tab title="Script">
    A script automation runs your code. Use a script to:

    - Run deterministic tasks, such as pinging a health check or posting a fixed reminder, without calling a model.
    - Start and coordinate agent conversations, such as one conversation per new issue, and use a model only for
      the steps that need judgment.

    Some templates install a script automation. When you ask for a task that doesn't need a model, the agent
    suggests a script.
  </Tab>
</Tabs>

## Write Good Automation Prompts

The prompt is what the agent runs each time the automation runs. Write it like instructions to a capable assistant.

### Be Specific

<Tabs>
  <Tab title="❌ Too Vague">
    ```
    Generate a report
    ```
  </Tab>
  <Tab title="✅ Clear & Actionable">
    ```
    Generate a weekly status report that:
    1. Lists all GitHub PRs merged in the last 7 days
    2. Summarizes open issues by priority
    3. Formats everything as markdown
    4. Posts to the #team-updates Slack channel
    ```
  </Tab>
</Tabs>

### Include Where to Send Results

Tell the automation what to do with its output:

- "Post to the #alerts Slack channel" (requires a Slack [MCP server](/overview/model-context-protocol))
- "Save to `reports/weekly-summary.md`"
- "Create a GitHub issue with the findings"

### Specify Error Handling

For monitoring tasks, explain what should happen when things go wrong:

```
Check the health endpoint at https://api.example.com/health.
If it returns anything other than 200 OK, send an alert to #ops
with the status code and response body.
If it's healthy, just log success without alerting.
```

## What Your Automation Can Access

Each run has the same access as a normal conversation on the same backend:

- **Terminal and files**: Run commands and create, read, and modify files.
- **Your model**: The model or Agent Profile set on the automation.
- **Your secrets**: API keys stored in your secrets settings.
- **MCP servers**: The MCP servers you configured.
- **Git access**: The Git providers you connected. On OpenHands Cloud and Enterprise, this includes the provider you
  signed in with.
- **Network access**: HTTP requests to external APIs.

Give an automation only the access it needs. Event payloads can contain text from anyone who can open an issue or
post a comment, so treat them as data, not instructions.

## Schedules

Describe the schedule in plain language:

- "every weekday at 9 AM"
- "every Monday morning"
- "hourly"
- "first day of each month"

The agent converts the description to a cron schedule. You can also give a cron expression directly, such as
`0 9 * * 1-5`. Schedules use UTC unless you name a timezone.

Cron fields also accept a single-start step, written as `start/step`. The validator expands it from the start value
up to the field maximum, so `2/2` in the month field means February, April, June, August, October, and December. A
step with a wildcard start, such as `*/2`, remains valid.

## Run Timeouts

Each run stops after its timeout. The default is 10 minutes. The maximum depends on the deployment. To change it,
ask for a different timeout, for example: "Use a 20-minute timeout."
