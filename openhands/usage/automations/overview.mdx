An automation runs work for you on a schedule or when an event happens. A run can be a single agent conversation, a
script that never calls a model, or code that starts and coordinates several agent conversations. Use automations to
review pull requests when they open, triage new issues, post a weekly report, or fix a failing build. Conversations
that a run starts appear in your conversations list, where you can open, review, and continue them.

Automations are available in Agent Canvas (open source), OpenHands Cloud, and OpenHands Enterprise. You create and
manage them the same way in each product. The products differ in how event webhooks reach your automations, what
limits apply to runs, and who owns and can see an automation. See [Where Automations Run](#where-automations-run).

## How Automations Work

Every automation has a trigger and an action.

- **Trigger**: A **schedule** runs the automation at set times, such as every weekday at 9 AM. An **event** runs it
  when an external service sends a webhook, such as a pull request opening on GitHub or a new issue in Linear.
- **Action**: A **prompt** runs one agent conversation. The agent has the same tools as a normal conversation: a
  terminal, file editing, your model, your secrets, and your MCP servers. Add plugins to give the agent extra skills
  and commands. A **script** runs your code. Use a script for deterministic work that doesn't need a model, or to
  start and coordinate several agent conversations from one run.

The automation service stores your automations, starts runs on schedule, and receives webhooks. Each run executes
on an Agent Server, the same backend that runs your conversations.

## Create an Automation

Review an automation in the setup form, or ask the agent in a regular conversation and confirm in chat. See
[Creating Automations](/openhands/usage/automations/creating-automations) for details.

- **Start from a template**: Pick a pre-built automation, such as a pull request reviewer or a Slack channel
  monitor, and fill in its fields.
- **Turn on automation mode**: Use the automation toggle in the Agent Canvas chat to tell the agent that you want an
  automation, then describe it.
- **Fill in the setup form**: Set the name, prompt, trigger, model, repositories, and plugins yourself. A
  conversation stays open beside the form, so you can ask the agent to fill in or change fields at any time.
- **Ask in any conversation**: Ask the agent to create an automation. It drafts one and asks you to confirm before
  it creates it.

## Where Automations Run

| | Agent Canvas (open source) | OpenHands Cloud | OpenHands Enterprise |
|---|---|---|---|
| **Scheduled automations** | Run while your backend is running | Always on | Always on |
| **Event automations** | Require a publicly reachable backend | Public webhook URL included | Public webhook URL and built-in integration events |
| **Ownership** | Your backend | Your account | Organization or personal |
| **Limits** | Your backend's resources | Cloud conversation limits | Budgets set by administrators |

<Tabs>
  <Tab title="Agent Canvas">
    Automations run on the [active backend](/openhands/usage/agent-canvas/backends). Backends that the
    `agent-canvas` launcher starts include the automation service. Manage automations in the
    [Automate view](/openhands/usage/agent-canvas/managing-automations), and use
    [Git Sync](/openhands/usage/agent-canvas/git-sync) to keep their definitions in a repository.

    Scheduled automations run only while the backend is running. If you run the backend on your laptop, runs
    stop when the laptop sleeps or shuts down. For automations that run around the clock, we recommend
    [running the backend on a VM](/openhands/usage/agent-canvas/backend-setup/vm).

    Event automations need a backend that external services can reach over the internet. Run the backend on a
    VM and expose it with a tunnel such as ngrok, as described in
    [Make a Local Backend Reachable](/openhands/usage/agent-canvas/automation-events#make-a-local-backend-reachable).
    If you can't expose the backend, use a scheduled automation that polls the service's API instead.
  </Tab>
  <Tab title="OpenHands Cloud">
    OpenHands Cloud is the free hosted version of OpenHands at [app.all-hands.dev](https://app.all-hands.dev).
    It runs your automations on hosted infrastructure, so scheduled automations keep running when your computer
    is off.

    Cloud gives each event source a public webhook URL, so event automations work without a tunnel or a VM.

    OpenHands Cloud limits how many conversations you can run. Every conversation that an automation starts counts
    toward that limit, including each conversation that a script starts. Choose schedules and event filters with
    that limit in mind. For deterministic tasks, use a script that doesn't start a conversation.
  </Tab>
  <Tab title="OpenHands Enterprise">
    OpenHands Enterprise runs automations on your own infrastructure, with the same features as OpenHands Cloud
    plus controls for teams:

    - **Organization and personal automations**: Automations that you create in an organization are visible to
      its members, and runs open read-only for members who don't own them. See
      [Automations in Enterprise](/enterprise/automations).
    - **Run identity**: Runs execute as the user who created the automation, or as a
      [service account](/enterprise/automations/service-accounts) that the organization controls.
    - **Roles**: Owners and Admins can manage any automation in the organization. Members manage only their own.
    - **Built-in events**: GitHub, Jira Data Center, Bitbucket Data Center, and Azure DevOps integrations deliver
      events without a separate webhook. See [GitHub Event Automations](/enterprise/automations/github-events)
      and [Data Center Event Automations](/enterprise/automations/data-center-events).

    Administrators turn on the automation service as part of the deployment. For Kubernetes, see
    [Automations](/enterprise/k8s-install/automations).
  </Tab>
</Tabs>

#### Daily GitHub Summary

```
Create an automation called "Daily GitHub Summary" that runs every weekday at 9 AM Eastern.

It should:
1. Summarize PRs opened, merged, and reviewed in the last 24 hours
2. List any PRs that have been open for more than 3 days
3. Format as a clean markdown summary
4. Post to the #engineering Slack channel
```

#### Weekly Metrics Report

```
Create an automation called "Weekly Metrics" that runs every Monday at 9 AM.

It should generate a weekly report covering:
- GitHub activity (commits, PRs merged, issues closed)
- Open issues grouped by priority
- PRs awaiting review for more than 3 days

Save the report to weekly-reports/ with the current date in the filename.
```

#### SSL Certificate Monitor

```
Create an automation called "SSL Monitor" that runs daily at 8 AM.

It should check SSL certificate expiry for these domains:
- api.example.com
- app.example.com
- www.example.com

If any certificate expires within 30 days, alert #devops with the domain and days remaining.
```

#### Weekly Cleanup

```
Create an automation called "Weekly Cleanup" that runs every Sunday at 2 AM UTC.

It should:
1. Find and delete temporary files older than 7 days
2. Create a summary of what was removed (file paths and sizes)
3. Post the cleanup summary to #ops
```

#### Backup Verification

```
Create an automation called "Backup Check" that runs daily at 6 AM.

It should verify that database backups exist and were created within the last 24 hours.
List the most recent backup for each database with its timestamp and size.
If any backup is missing or stale, send an urgent alert to #alerts.
```

#### Analytics Data Sync

```
Create an automation called "Analytics Sync" that runs every 6 hours.

It should:
1. Pull the latest data from our analytics API
2. Update metrics.json with the new data
3. Calculate week-over-week changes for key metrics
4. If any metric changed by more than 20%, flag it in a summary message
```

## Tips for Writing Good Prompts

<AccordionGroup>
  <Accordion title="Be specific about actions">
    Tell the automation exactly what to do:
    - "Check X and if Y, then Z"
    - "Generate a report and save it to..."
    - "Fetch data, compare with expected values, and report differences"
  </Accordion>
  <Accordion title="Include error handling">
    Specify what should happen when things go wrong:
    - "If the response is not 200..."
    - "If any backup is missing..."
    - "If the check fails, alert the team"
  </Accordion>
  <Accordion title="Define where results go">
    Be explicit about outputs:
    - "Post to the #channel Slack channel"
    - "Save to reports/ with the current date"
    - "Create a GitHub issue with the findings"
  </Accordion>
</AccordionGroup>
