Event-based automations run when something happens, such as a webhook firing, instead of on a schedule. This is ideal for reacting to events from external services like Linear, Stripe, or Slack.

This page applies to the local Agent Canvas and OpenHands Enterprise. The walkthrough starts with the local Agent Canvas.

<Info>
  For GitHub events such as pull requests, issues, and comments, OpenHands Enterprise has a built-in
  integration that needs no webhook registration. See
  [GitHub Event Automations](/enterprise/automations/github-events).
</Info>

## Built-In vs. Custom Integrations

| Type | Setup | Best For |
|------|-------|----------|
| **Built-in (GitHub)** | One-time org setup, then create the automation. See [GitHub Event Automations](/enterprise/automations/github-events) | PR reviews, issue triage, push-triggered tasks |
| **Custom Webhooks** | Register webhook first, then create automation | Linear, Stripe, Slack, and other services |

## Custom Webhooks

For services other than GitHub, such as Linear, Stripe, or Slack, register a custom webhook first, then create automations that use it.

<Note>
**Two-phase workflow for custom webhooks:**

1. **Webhook registration (one-time setup)**: You execute the curl command yourself to register the webhook. This keeps your signing secrets secure—the agent provides the command but never handles your credentials directly.

2. **Automation creation (repeatable)**: Once the webhook is registered, the agent can create, update, and manage automations for that webhook source conversationally—no manual curl commands needed.
</Note>

### Before You Start on Agent Canvas

The external service sends events to your automation service over the internet, so a custom webhook needs a URL that the service can reach. A backend running on `localhost` is not reachable, so make it publicly reachable first:

- **Expose the backend.** Run your backend with `--public` and put a tunnel such as [ngrok](https://ngrok.com/) in front of it. See [VM / Self-Hosted Installation](/openhands/usage/agent-canvas/backend-setup/vm#option-b-ngrok-without-oauth) for the commands.
- **Know your backend URL and API key.** Use the same **Host / Base URL** and API key you entered in **Manage Backends**. Commands on this page call `<backend URL>/api/automation/v1/...` with the key in the `X-Session-API-Key` header.

<Warning>
Exposing the backend puts the whole agent server on the internet. Use a strong `LOCAL_BACKEND_API_KEY`, and do not share the API key or the webhook signing secret.
</Warning>

<Tip>
If you can't expose your machine, use a [cron-based automation](/openhands/usage/automations/overview) that polls the service's API on a schedule instead of a webhook.
</Tip>

### Walkthrough: Linear Integration

<Note>
This example sets up a Linear webhook that auto-triages new issues. The registration command has a tab for the local Agent Canvas and one for OpenHands Enterprise.
</Note>

#### Step 1: Get Your Webhook Secret from Linear

Linear provides the webhook signing secret—you cannot configure your own.

1. Go to **Linear Settings → API → Webhooks**
2. Click **New webhook**
3. Copy the **signing secret** that Linear displays (you'll need this in the next step)
4. Leave the webhook URL blank for now—you'll get it from OpenHands

#### Step 2: Register the Webhook with OpenHands

<Tabs>
  <Tab title="Local Agent Canvas">
    <Warning>
    The Agent Canvas backend must be reachable by the service that sends the events. Linear, Stripe, Slack, and similar services deliver webhooks from the internet, so they can't reach `localhost` or a private network address. Expose the backend with a tunnel or public URL first, as described in [Before You Start on Agent Canvas](#before-you-start-on-agent-canvas), and use that public URL as `OPENHANDS_HOST` below.
    </Warning>

    Export your backend URL, your backend API key, and the webhook secret from Step 1:

    ```bash
    export OPENHANDS_HOST="https://your-domain.ngrok-free.app"   # your public backend URL
    export OPENHANDS_SESSION_API_KEY="your-backend-api-key"
    export LINEAR_WEBHOOK_SECRET="your-linear-signing-secret-from-step-1"
    ```

    Then register the webhook:

    ```bash
    curl -X POST "${OPENHANDS_HOST}/api/automation/v1/webhooks" \
      -H "X-Session-API-Key: ${OPENHANDS_SESSION_API_KEY}" \
      -H "Content-Type: application/json" \
      -d '{
        "name": "Linear Issues",
        "source": "linear",
        "event_key_expr": "type",
        "signature_header": "Linear-Signature",
        "webhook_secret": "'"${LINEAR_WEBHOOK_SECRET}"'"
      }'
    ```

    <Tip>
    **Where do I find my backend API key?** `your-backend-api-key` is the API key for your Agent Canvas backend. It is the same key that you enter in the **API Key** field in **Manage Backends**. How you find it depends on how the backend runs:

    - **You set `LOCAL_BACKEND_API_KEY`:** use that value.
    - **Docker:** use the `LOCAL_BACKEND_API_KEY` value you passed to the container. If you didn't set one, the server generates a key. Check the container logs for it.
    - **Default local backend:** if Agent Canvas generated the key, it is stored in `~/.openhands/agent-canvas/api-key.txt`. Run `cat ~/.openhands/agent-canvas/api-key.txt` to print it.
    - **VM or self-hosted backend:** use the `LOCAL_BACKEND_API_KEY` you configured on that machine. See [VM / Self-Hosted Installation](/openhands/usage/agent-canvas/backend-setup/vm).

    This key gives full access to the backend, so keep it private.
    </Tip>

    <Note>
    The `webhook_url` in the response is built from the automation service's own address, so on a local backend it can start with `http://localhost`. External services can't reach that address. In Step 3, keep the path (`/api/automation/v1/events/<org_id>/linear`) and replace the beginning with your public backend URL.
    </Note>
  </Tab>
  <Tab title="OpenHands Enterprise">
    Generate an API key in OpenHands Enterprise under **Settings → API Keys**, then export it with your instance URL and the webhook secret from Step 1:

    ```bash
    export OPENHANDS_HOST="https://your-openhands-enterprise-host"
    export OPENHANDS_API_KEY="your-openhands-api-key"
    export LINEAR_WEBHOOK_SECRET="your-linear-signing-secret-from-step-1"
    ```

    Then register the webhook:

    ```bash
    curl -X POST "${OPENHANDS_HOST}/api/automation/v1/webhooks" \
      -H "Authorization: Bearer ${OPENHANDS_API_KEY}" \
      -H "Content-Type: application/json" \
      -d '{
        "name": "Linear Issues",
        "source": "linear",
        "event_key_expr": "type",
        "signature_header": "Linear-Signature",
        "webhook_secret": "'"${LINEAR_WEBHOOK_SECRET}"'"
      }'
    ```

    The response includes the `webhook_url` that you'll configure in Linear.
  </Tab>
</Tabs>

<Accordion title="Understanding event_key_expr">
The `event_key_expr` is a JMESPath expression that extracts the event type from incoming webhook payloads. This extracted value is what you match against in the automation's `on` field.

For example, Linear sends payloads like:
```json
{"type": "Issue", "action": "create", "data": {...}}
```

With `event_key_expr: "type"`, the system extracts `"Issue"` as the event type. Then in your automation, you set `on: "Issue"` to match it.
</Accordion>

<Tip>
If you're integrating a service that lets you configure the signing secret (unlike Linear), you can omit `webhook_secret` from the request. The automation service will generate one and return it in the response—store it securely, as it's shown only once.
</Tip>

#### Step 3: Complete the Linear Webhook Configuration

1. Return to the Linear webhook you started in Step 1
2. Paste the `webhook_url` from the previous step. On a local Agent Canvas, use the public version of the URL, as described in the note above
3. Select which events to send (e.g., Issues, Comments)
4. Save the webhook

#### Step 4: Create the Automation

Now the webhook is registered, the agent can create automations for you end-to-end. Just describe what you want. On Agent Canvas, you can do this in the [setup assistant](/openhands/usage/agent-canvas/managing-automations#create-an-automation-with-the-setup-assistant):

```
Create an event-based automation called "Triage Linear Issues" that triggers
when a new issue is created in Linear.

It should analyze the issue title and description, suggest appropriate labels,
and add a comment with initial triage notes.
```

The agent creates the automation with:
- **Source**: `linear` (your registered webhook)
- **Event**: `Issue` (Linear's event type)
- **Filter**: `action == 'create'`

### Filtering Events

Filters let you narrow which events trigger your automation. They use [JMESPath expressions](https://jmespath.org/) to match fields in the event payload—so you can trigger only on specific labels, users, branches, or other conditions.

<Note>
OpenHands extends standard JMESPath with custom functions including `icontains` (case-insensitive string match) and `glob` (wildcard path matching). It also supports `!` (negation), `&&` (AND), and `||` (OR) as boolean operators. These extensions are not part of the [JMESPath specification](https://jmespath.org/specification.html).
</Note>

**Common filter patterns:**

```
contains(pull_request.labels[].name, 'openhands')

icontains(comment.body, '@openhands')

glob(repository.full_name, 'myorg/*')

ref == 'refs/heads/main'

glob(repository.full_name, 'myorg/*') && contains(pull_request.labels[].name, 'bug')
```

- `contains(...)` — match a specific label
- `icontains(...)` — case-insensitive mention in a comment body
- `glob(...)` — match repos in your org with wildcards
- `==` — exact match (e.g., push to main branch only)
- `&&` — combine multiple conditions

### Custom Webhook Parameters

When registering any custom webhook, these parameters define how OpenHands processes incoming events:

| Parameter | Required | Description |
|-----------|----------|-------------|
| `name` | Yes | Human-readable name |
| `source` | Yes | Unique identifier (lowercase, alphanumeric with hyphens) |
| `event_key_expr` | No | JMESPath to extract event type (default: `type`) |
| `signature_header` | No | Header containing HMAC signature (default: `X-Signature-256`) |
| `webhook_secret` | No | Signing secret—provide yours or let the system generate one |

### Common Services

These are example configurations for popular services. **Always verify with each service's webhook documentation**, as signature headers and payload formats may change.

| Service | Signature Header | Event Key | Notes |
|---------|-----------------|-----------|-------|
| Linear | `Linear-Signature` | `type` | |
| Stripe | `Stripe-Signature` | `type` | Uses a custom `t=timestamp,v1=signature` format — verify compatibility |
| Slack | `X-Slack-Signature` | `type` | |
| Twilio | `X-Twilio-Signature` | `type` | Uses HMAC-SHA1 of request URL + params — verify compatibility |
