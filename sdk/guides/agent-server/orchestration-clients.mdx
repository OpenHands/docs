Use `Conversation` and `Workspace` for ordinary agent applications. Use
`AgentServerClient` or `AsyncAgentServerClient` when a dispatcher must create a
conversation from a saved profile, start a bundle without waiting for it, inspect
its command result, or release its runtime while retaining history.

The SDK owns HTTP routes, authentication headers, and conversation scope. The
caller owns scheduling, admission limits, workflow selection, and completion
policy. Canvas uses the TypeScript client for the same API boundary.

## Provision and Dispatch a Conversation

The server advertises `conversation_runtime`. A dispatcher selects the appropriate
workspace location, then supplies the same run environment to the bundle in both
local and Docker modes. The automation itself does not branch on workspace kind.

```python
import os
from pathlib import Path
from uuid import uuid4

from openhands.sdk.client import AsyncAgentServerClient


async def dispatch(bundle: bytes):
    server = AsyncAgentServerClient(
        os.environ["AGENT_SERVER_URL"], os.environ["SESSION_API_KEY"]
    )
    conversation_id = str(uuid4())
    try:
        info = await server.get_server_info()
        isolated = info["conversation_runtime"] == "docker"
        working_dir = "/workspace" if isolated else str(
            Path(os.environ["WORKSPACE_BASE"]) / conversation_id
        )
        await server.create_conversation(
            conversation_id=conversation_id,
            agent_profile_id=os.environ["AGENT_PROFILE_ID"],
            working_dir=working_dir,
            title="Scheduled automation",
            tags={"automationrun": conversation_id},
        )
        runtime = server.runtime(conversation_id)
        await runtime.upload(f"{working_dir}/bundle.tar.gz", bundle)
        # A dispatcher extracts the bundle and supplies its configured environment
        # before starting its entrypoint. Keep command construction in the dispatcher.
        return conversation_id, working_dir
    finally:
        await server.aclose()
```

`runtime.start(command, timeout=...)` returns a command record immediately.
`runtime.get_output(command_id)` returns the latest matching output page; an empty
page or an output with no exit code means the command has not completed.
`runtime.execute(command, timeout=..., cwd=...)` waits for a foreground command.
Always verify the actual command's exit code before accepting completion.

## The Bundle Interface

Supply `AGENT_SERVER_URL`, `SESSION_API_KEY`, `AUTOMATION_CONVERSATION_ID`, and
`WORKSPACE_BASE` to each bundle. The same code works in either workspace:

```python
import os
from contextlib import closing
from uuid import UUID

import openhands.tools  # Register standard tool event schemas.
from openhands.sdk import RemoteConversation, RemoteWorkspace
from openhands.sdk.conversation.response_utils import get_agent_final_response

with RemoteWorkspace(
    host=os.environ["AGENT_SERVER_URL"],
    api_key=os.environ["SESSION_API_KEY"],
    working_dir=os.environ["WORKSPACE_BASE"],
) as workspace:
    with closing(RemoteConversation.attach(
        workspace, UUID(os.environ["AUTOMATION_CONVERSATION_ID"])
    )) as conversation:
        conversation.send_message("Perform the configured workflow.")
        conversation.run(timeout=2400)
        print(get_agent_final_response(conversation.state.events))
```

`attach` reads the existing server-resolved agent, including an ACP agent. It
fails if the conversation is missing or inaccessible; it does not create a new
conversation or reload profile settings and secrets. Run completion, callbacks,
events, and errors follow the ordinary SDK conversation lifecycle. Closing the
attachment preserves the server conversation and the caller-owned workspace.
Import the tool packages used by the remote agent so their event schemas are
registered, just as when constructing an agent locally.

Both clients expose `set_title(conversation_id, title)` and
`search_events(conversation_id, kind=..., limit=..., page_id=...)`. Event searches
return the server page unchanged, including raw structured tool arguments and
`next_page_id`, in newest-first order. `get_errors` uses the same event search.
Their runtime clients expose
upload, execute, start, output retrieval, credential handoff, and release.
An explicit conversation UUID binds runtime operations to that conversation.
Calling `runtime()` without an ID selects the legacy host runtime; lifecycle
operations are unavailable in that unscoped form.

## Select Secrets With an Agent Profile

Profile secret selection requires the profile `secret_refs` and Docker integration
changes tracked in [SDK #5014](https://github.com/OpenHands/software-agent-sdk/issues/5014).
Keep this section unpublished until that integration is released.

Set `secret_refs` on the saved agent profile to an explicit list of secret names,
for example `["GITHUB_REVIEWER_TOKEN"]`. The profile stores names only. A launch
using that profile receives the selected saved secrets without the dispatcher
copying every secret into the request. An empty list permits no user secrets;
`null` preserves the existing request-only, unrestricted behavior.

The Agent Server applies the same selection before local conversation construction
and before Docker secret materialization. Extra request secrets are discarded
before their lookup runs. For a selected name present in the server's secret store,
the stored value takes precedence over a caller-supplied value or lookup. Names
missing from the store can still match explicitly supplied conversation secrets.
The agent's secret registry advertises selected names and descriptions in the
system prompt and exports selected values to tools when needed. Values are never
included in the prompt. Docker handoff encrypts them with the runtime's key.

LLM profile credentials and selected MCP credentials have their own delivery
channels. Restrict `mcp_server_refs`, tools, and other profile capabilities as well.
A secret allow-list does not narrow the external provider's token permissions:
issue repository-scoped credentials appropriate to each automation's role.

## Credentials and Lifecycle Ownership

Only a trusted orchestrator should call `runtime.get_session_key()`. On a Docker
server supporting credential handoff, it returns the selected inner runtime's key.
The dispatcher supplies that key and the runtime-reachable server URL to the
worker. Keep the outer control-plane key outside the worker.

Local workspaces retain the local server's credential boundary and are not
security sandboxes. Use Docker isolation and role-scoped external-service grants
when running untrusted repository code.

After a Docker run has stopped and its result is recorded, the dispatcher calls
`runtime.release()`. This releases that runtime while preserving conversation
history. A missing runtime is treated as already released; other failures are
reported. A persistent local server should be retained by its owner.

An HTTP client supplied through `http_client=` remains caller-owned. Otherwise,
call `close()` or `aclose()` to release the SDK client's connections. None of these
methods chooses a workflow, posts an acceptance decision, or schedules a run.
