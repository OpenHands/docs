Agents in OpenHands Enterprise can run their own Docker daemon inside the sandbox. Use it to have an
agent start your application with Docker Compose for testing, build and run an image to verify a
`Dockerfile` change, or use build and test tools that ship as container images.

## Requirements

- OpenHands Enterprise 0.18.2 or later.
- The Sysbox sandbox runtime, on nodes running Linux kernel 6.3 or newer (for example, Ubuntu 24.04).
  - On Kubernetes, install Sysbox on your sandbox node pool as described in
    [Installing Sysbox](/enterprise/k8s-install/sysbox). Sysbox isn't yet supported on AKS, so Docker
    in the sandbox isn't available there.
  - On a VM install, Sysbox is the default **Sandbox Isolation** setting in the installer. The
    installer's preflight checks verify the kernel version.
- A sandbox image with Docker, Buildx, and the Compose plugin. The standard sandbox image includes
  them. If you use a [custom sandbox image](/enterprise/custom-sandbox-images), build it from the
  standard base image.

## Security

Each sandbox runs under Sysbox, which isolates the sandbox from the host node. The Docker daemon and
the containers it starts stay inside that sandbox:

- **No privileged mode**: The sandbox doesn't run as a privileged container.
- **No host Docker socket**: The sandbox runs its own Docker daemon. The host's Docker socket isn't
  mounted, so the agent can't reach the host's containers or images.
- **Non-root**: Sandbox processes run as a non-root user, and nested containers run in a user
  namespace. Root inside a nested container isn't root on the node.
- **One pod per sandbox**: Containers an agent starts stay in its sandbox and aren't shared with
  other agents, users, or the cluster.
- **No cluster credentials**: Sandbox pods don't mount a Kubernetes service account token.
- **No host networking**: Sandbox pods use the cluster pod network, not the node's network namespace.
- **Set by the operator**: The sandbox runtime is set in the deployment through a Kubernetes
  [`RuntimeClass`](https://kubernetes.io/docs/concepts/containers/runtime-class/). Agents and users
  can't change it.

To control which networks sandboxes can reach, use the network controls around your deployment, such
as subnet placement, security groups, or firewall rules.

## Use Docker From an Agent

Ask the agent to use Docker in a normal conversation. The agent starts the daemon with `sudo dockerd`
the first time it needs Docker. Running `sudo` in the sandbox is safe: Sysbox maps root in the
sandbox to an unprivileged user on the host (see [Security](#security)).

<Steps>
  <Step title="Confirm Docker is available">
    ```text
    Start the Docker daemon if it isn't running, then show me `docker version`
    and confirm the daemon is reachable.
    ```

    The output should include both a Client and a Server section.
  </Step>

  <Step title="Run a stack with Docker Compose">
    ```text
    Create a docker-compose.yml with a single nginx service mapping host port 8080
    to container port 80. Run `docker compose up -d`, then curl http://localhost:8080
    and show me the HTTP status code. When you're done, run `docker compose down`.
    ```

    The agent should report status `200`.
  </Step>

  <Step title="Build and run an image">
    ```text
    Create a Dockerfile based on alpine whose command prints "hello-from-built-image".
    Build it as demo:latest, then run it and show me the output.
    ```

    The output should be `hello-from-built-image`.
  </Step>
</Steps>

You don't need to spell out each command. For your own projects, a request such as "Start our app
with Docker Compose and check that the homepage loads" is usually enough.
