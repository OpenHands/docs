Automations run OpenHands on a schedule or in response to events, such as reviewing a pull request
when it opens. In OpenHands Enterprise, automations belong to an organization and, by default, are
shared with every member of that organization.

This page explains how automations behave inside an organization. To create, browse, run, and
manage automations, see [Managing Automations](/openhands/usage/agent-canvas/managing-automations).

## How Automations Work in OpenHands Enterprise

| Behavior | Summary |
| --- | --- |
| Visibility | By default, every member of the organization can see an automation. An automation that runs as a person can be made private |
| Run conversations | Members can view the conversations that automation runs start, in read-only mode |
| Run identity | Each run executes as the user who created the automation, or as a service account |
| Management | Owners and Admins can manage any automation; Members can manage only the automations they created |

## Automations Are Visible to the Whole Organization

By default, an automation is visible to all members of its organization.

Automations often power parts of the software development lifecycle, such as code review, issue
triage, and dependency upgrades. Everyone who works in that lifecycle needs to understand what is
automated, when it runs, and what it does. Sharing automations across the organization makes that
behavior transparent.

<Warning>
  Because every organization member can see an automation's configuration and the conversations it
  starts, do not put secret values in automation prompts. Store credentials as secrets instead.
</Warning>

## Private Automations

An automation that runs as a person can be private. When you create or edit an automation that runs
as you, choose its `Visibility` in the automation's settings:

| Visibility | Who can see the automation |
| --- | --- |
| Organization (default) | Every member of the organization |
| Private | The person the automation runs as, Owners, and Admins |

Other members do not see a private automation in the automations list, and can't open it, its
activity log, or its stored data.

Private limits who can see an automation. It does not change who can manage it: Owners and Admins
can still edit, disable, or delete a private automation.

An automation that runs as a [service account](/enterprise/automations/service-accounts) is always
visible to the organization. When an Owner or Admin changes a private automation to run as a service
account, it becomes visible to the organization.

<Note>
  Private does not hide everything an automation produces:

  - A run's conversation still opens in read-only mode for any organization member who has its link,
    for example a link the automation posts in a pull request comment.
  - If the organization uses [Git Sync](/openhands/usage/agent-canvas/git-sync), private automations
    are exported to the Git Sync repository like any other automation.

  The warning above still applies: do not put secret values in the prompt of a private automation.
</Note>

## Automation Conversations Are Read-Only for Other Members

The conversations started by automation runs are also visible to all organization members. Members
who did not create the automation see these conversations in read-only mode. They can follow the
full conversation history, but cannot send messages to the agent or change the automation.

For example, an automation that reviews GitHub pull requests may post a link to its conversation in
the review comment. Any member of the organization can open that link to see the details of what
the agent found.

## Who Automations Run As

Every automation run executes under an identity. By default, that identity is the user who created
the automation. Owners and Admins can make an automation run as a
[service account](/enterprise/automations/service-accounts) instead, so it keeps running when people
leave the organization.

To see who an automation runs as, open the automation and check the `Automation Runs As` field in
its details.

## Who Can Manage Automations

Who can edit, disable, or delete an automation depends on the user's
[organization role](/openhands/usage/cloud/organizations/roles-permissions):

| Action | Member | Admin | Owner |
| --- | :---: | :---: | :---: |
| View automations that are visible to the organization, and their run conversations | ✓ | ✓ | ✓ |
| View private automations that run as another user | | ✓ | ✓ |
| Edit, disable, or delete automations they created | ✓ | ✓ | ✓ |
| Edit, disable, or delete automations created by other users | | ✓ | ✓ |

Members can't edit, disable, or delete an automation that runs as a service account, even one they
created.

Owners and Admins can act on automations on behalf of other users. For example, an Admin can turn
off an automation created by a user who is no longer available to maintain it.
