OpenHands Enterprise can be deployed in three ways. Choose the option that matches your goal and the
infrastructure you have access to.

## Docker Compose

[Docker Compose](/enterprise/docker-compose) gets you a quick evaluation environment for fewer than
10 users on a single machine.

- Sandboxes run as Docker containers on the same machine as OpenHands.
- Some features are off by default, including budgeting, the built-in LiteLLM gateway, and the
  sandboxing infrastructure used by production deployments.

Use Docker Compose to evaluate OpenHands Enterprise, not to run it in production.

## Helm Install

[Helm install](/enterprise/k8s-install/index) deploys OpenHands Enterprise into your own Kubernetes
cluster. It is the **recommended production path**.

- Scales with your cluster.
- Includes budgeting, the built-in LiteLLM gateway, and sandboxing infrastructure.
- Supports a durable production database, such as [external PostgreSQL](/enterprise/external-postgres).

## Replicated VM

[Replicated VM](/enterprise/vm-install/generic-vm) offers a production path without having to manage
Kubernetes. It is a good fit for organizations that want to deploy to production but do not have
access to Kubernetes resources.

- Includes budgeting, the built-in LiteLLM gateway, and sandboxing infrastructure.
- Configured through the Replicated Admin Console.
- Scalability can be limited compared to Helm. See the [Sizing Guide](/enterprise/sizing-guide) to
  plan capacity.

## Enabled by Default

The table below shows which features are on by default for a fresh deployment.

| Feature | Docker Compose | Helm Install | Replicated VM |
|---|:---:|:---:|:---:|
| Agent Canvas UI | ✅ | ✅ | ✅ |
| Automations | ✅ | ✅ | ✅ |
| OAuth V2 Login | ✅ | ✅ | ✅ |
| Built-in LiteLLM gateway | ❌ | ✅ | ✅ |
| Sandboxing infrastructure | ❌ | ✅ | ✅ |

## Upgrade Scenarios

Existing Helm and Replicated VM deployments keep their current settings when upgraded, so features
that are on by default for fresh deployments may be off. After upgrading, you may need to enable
the following. The Docker Compose column lists the equivalent variables for reference.

| Feature | Replicated VM (Admin Console) | Helm (chart values) | Docker Compose (`app` service environment) |
|---|---|---|---|
| Super Admin Dashboard | `Experimental` > `Enable Super Admin Dashboard` | `env.ENABLE_SUPER_ADMIN: "1"`<br/>`env.OH_WEB_CLIENT_FEATURE_FLAGS_ENABLE_SUPER_ADMIN: "1"` | `ENABLE_SUPER_ADMIN: '1'`<br/>`OH_WEB_CLIENT_FEATURE_FLAGS_ENABLE_SUPER_ADMIN: '1'` |
| OAuth V2 Login | `Experimental` > `Enable OAuth V2 Login` | `env.ENABLE_OAUTH_V2_LOGIN: "1"`<br/>`env.OH_WEB_CLIENT_FEATURE_FLAGS_ENABLE_OAUTH_V2_LOGIN: "1"` | `OH_WEB_CLIENT_FEATURE_FLAGS_ENABLE_OAUTH_V2_LOGIN: '1'` |
| Automations | `Automations` > `Enable Automations` | `automation.enabled: true`, plus the related values in [Enable Automations with Helm](/enterprise/k8s-install/automations) | The `automation-server` service, plus `AUTOMATION_SERVICE_URL` and `AUTOMATION_EVENT_FORWARDING_ENABLED: 'true'` |

<Note>
  Enabling OAuth V2 Login removes Keycloak as a dependency.
</Note>

On Replicated VM, change these settings in the Admin Console, then deploy the new configuration. See
[Admin Console Configuration](/enterprise/vm-install/admin-console-configuration).

On Helm, set both forms of each flag. The server reads the bare variable, such as
`ENABLE_SUPER_ADMIN`, and the web client reads the `OH_WEB_CLIENT_FEATURE_FLAGS_` variable. Add them
under the top-level `env` key of your values file, then run `helm upgrade`:

```yaml
env:
  ENABLE_SUPER_ADMIN: "1"
  OH_WEB_CLIENT_FEATURE_FLAGS_ENABLE_SUPER_ADMIN: "1"
  ENABLE_OAUTH_V2_LOGIN: "1"
  OH_WEB_CLIENT_FEATURE_FLAGS_ENABLE_OAUTH_V2_LOGIN: "1"
```

On Docker Compose, the `docker-compose.yml` file in the repository already sets these variables and
includes the `automation-server` service. To pick them up, [upgrade](/enterprise/docker-compose#upgrade)
by pulling the latest changes and restarting the stack.
