This guide explains how to connect Azure DevOps Services to an OpenHands
Enterprise installation. The integration lets users sign in with Microsoft
Entra ID, open Azure Repos, create branches and pull requests, and use Azure
Boards work items or pull request comments as context for OpenHands workflows.

<Note>
  This guide covers Azure DevOps Services at `https://dev.azure.com`. Azure
  DevOps Server is not covered by this integration.
</Note>

## Prerequisites

- An OpenHands Enterprise installation using Replicated or standalone Helm.
- A Microsoft Entra administrator who can register an application and create a
  client secret.
- An Azure DevOps Services organization, project, and repository.
- Azure DevOps users with access to the projects and repositories they will use
  with OpenHands.
- Network access from OpenHands to `login.microsoftonline.com` and
  `dev.azure.com`.
- If you plan to trigger automations from Azure DevOps Service Hooks, network
  access from Azure DevOps back to the OpenHands app URL or automation webhook
  URL.

## Register a Microsoft Entra Application

In the Azure portal, create a Microsoft Entra app registration for OpenHands.
These steps set up sign-in through Keycloak. If you use OAuth V2 login, also
follow [Use OAuth V2 Login](#use-oauth-v2-login).

1. Go to **Microsoft Entra ID > App registrations**.
2. Click **New registration**.
3. Enter a name such as `OpenHands Azure DevOps`.
4. Select the supported account type for your organization.
5. Add a **Web** redirect URI:

   ```text
   https://<your-auth-hostname>/realms/allhands/broker/azure_devops/endpoint
   ```

   Replace `<your-auth-hostname>` with your installation's Authentication
   hostname (`auth.<your-openhands-domain>` by default), for example
   `https://auth.openhands.example.com/realms/allhands/broker/azure_devops/endpoint`.

6. Click **Register**.
7. Copy the **Directory (tenant) ID** and **Application (client) ID**.
8. Go to **Certificates & secrets** and create a client secret. Copy the secret
   value before leaving the page.
9. If your tenant requires explicit API permissions, add the Azure DevOps
   delegated permission required for user access and grant admin consent.

OpenHands requests the following Microsoft identity scopes during sign-in:

```text
openid email profile offline_access https://app.vssps.visualstudio.com/.default
```

## Configure Azure DevOps Access

Make sure the users who will sign in to OpenHands have access to the Azure
DevOps organizations, projects, and repositories they need. OpenHands uses the
signed-in user's Azure DevOps access token for repository discovery and Git
operations. You don't configure an organization: each user sees every
organization they belong to.

Repository names in OpenHands use this format:

```text
organization/project/repository
```

For example:

```text
contoso/web/PetStore
```

## Configure the Admin Console

Pick the path that matches how OpenHands Enterprise is deployed.

<Tabs>
  <Tab title="Replicated">
    Open the Replicated Admin Console for your OpenHands Enterprise installation
    and go to the application configuration page.

    In **Azure DevOps Authentication**:

    1. Enable **Azure DevOps Authentication**.
    2. Enter the **Microsoft Entra Tenant ID**.
    3. Enter the **Azure DevOps Client ID**.
    4. Enter the **Azure DevOps Client Secret**.
    5. Save and deploy the updated configuration.
  </Tab>

  <Tab title="Standalone Helm">
    Set Azure DevOps values on the `openhands` and `openhands-secrets` charts.

    In your `values.yaml` for the `openhands` chart:

    ```yaml
    azureDevOps:
      enabled: true
      tenantId: "<your-microsoft-entra-tenant-id>"
      auth:
        existingSecret: azure-devops-app
    ```

    In your `values.yaml` for the `openhands-secrets` chart:

    ```yaml
    config:
      azure_devops_client_id: "<your-azure-devops-client-id>"
      azure_devops_client_secret: "<your-azure-devops-client-secret>"
    ```

    Then redeploy both charts. Deploying the `openhands-secrets` chart with
    these values creates the Kubernetes secret named `azure-devops-app`. The
    `openhands` chart reads the client ID and client secret from that secret via
    `azureDevOps.auth.existingSecret`. If you use a different secret name, set
    the same name in both charts.
  </Tab>
</Tabs>

## Sign In with Azure DevOps

After the deployment is completed, users choose **Sign in with Azure DevOps** on
your app's login page.

On first sign-in, Microsoft may ask the user to consent to the requested
permissions. After sign-in, OpenHands stores the user's Azure DevOps token
through the authentication provider so it can list repositories and run Git
operations as that user.

## Use OAuth V2 Login

With **Enable OAuth V2 Login** turned on in the **Experimental** section of the
Admin Console, OpenHands connects to Microsoft Entra directly instead of
through Keycloak. You configure Azure DevOps as an auth provider in the Super
Admin dashboard, which is turned on by **Enable Super Admin Dashboard** in the
same section.

### Configure the Auth Provider

1. Go to `https://<your-openhands-domain>/super-admin/auth-providers`.
2. Open the **Azure DevOps** provider if one is listed. Installations that
   already had Azure DevOps Authentication configured when they were upgraded
   get one automatically. Otherwise, click **Add Provider**, choose
   **Azure DevOps**, and click **Create Provider**.
3. Enter or confirm the **Client ID** and **Client Secret** from your Entra
   app registration. The page asks for the Client Secret again whenever you
   change other fields.
4. In **Authorization URL** and **Token URL**, use your Directory (tenant) ID.
   The **Azure DevOps** preset fills these in with a `YOUR_TENANT_ID`
   placeholder:

   ```text
   https://login.microsoftonline.com/<your-tenant-id>/oauth2/v2.0/authorize
   https://login.microsoftonline.com/<your-tenant-id>/oauth2/v2.0/token
   ```

5. Leave **Userinfo URL** empty. OpenHands reads the user's identity and email
   from the ID token that Microsoft returns with the access token.
6. Set **Scopes** to:

   ```text
   openid email profile offline_access 499b84ac-1321-427f-aa17-267ca6975798/vso.profile 499b84ac-1321-427f-aa17-267ca6975798/vso.code_write 499b84ac-1321-427f-aa17-267ca6975798/vso.project 499b84ac-1321-427f-aa17-267ca6975798/vso.work_write
   ```

7. To show a sign-in button for this provider on the login page, turn on
   **Use as OpenHands Authentication Provider**. Leave it off if users only
   connect Azure DevOps from **Settings** > **Integrations**.
8. Turn on **Enabled** and click **Save Changes**.
9. Copy the **Redirect URL** shown on the provider page. It has this form:

   ```text
   https://<your-openhands-domain>/oauth/<provider-id>/callback
   ```

10. In the Entra app registration, go to **Authentication** and add the
    Redirect URL as another **Web** redirect URI. Keep the Keycloak redirect
    URI if you still use Keycloak sign-in.

### About the Scopes

`499b84ac-1321-427f-aa17-267ca6975798` is the resource ID of Azure DevOps in
Microsoft Entra. It is the same in every tenant. Each
`499b84ac-1321-427f-aa17-267ca6975798/<scope>` entry requests one Azure DevOps
permission:

| Scope | Grants |
| --- | --- |
| `openid`, `email`, `profile` | The ID token with the user's identity and email. |
| `offline_access` | A refresh token. Without it, OpenHands can't renew the Azure DevOps token when it expires, and users must reconnect. |
| `vso.profile` | Read the user's profile and the organizations they belong to. |
| `vso.code_write` | Read and write code, branches, and commits, and create and manage pull requests. |
| `vso.project` | Read projects and teams. |
| `vso.work_write` | Read, create, and update work items and queries. |

Because OpenHands requests each permission by name, the app registration
doesn't need an Azure DevOps API permission. Each user sees a Microsoft consent
prompt the first time they connect. To skip the prompt, an administrator can
add the same Azure DevOps delegated permissions to the app registration and
grant admin consent for the tenant. If your tenant doesn't let users consent
to apps, an administrator must do this.

Don't replace these scopes with
`499b84ac-1321-427f-aa17-267ca6975798/.default`. That scope only returns
permissions already added to the app registration, so it fails with
`AADSTS650057` unless the Azure DevOps API permission is configured.

<Warning>
  Microsoft doesn't guarantee that the `email` claim is correct. Keep the
  Authorization URL and Token URL on your own tenant ID rather than `common`
  or `organizations`. If you allow other tenants, turn off **Link existing
  accounts by email** for this provider.
</Warning>

## Use Azure DevOps Repositories

After signing in, users can select Azure DevOps repositories from the OpenHands
repository picker. OpenHands can:

- List and search Azure DevOps repositories in every organization the signed-in
  user belongs to. Users who belong to only one organization see only that
  one.
- Clone Azure Repos using the signed-in user's OAuth token. SSH remote URLs (`git@ssh.dev.azure.com:v3/...`) are also recognized.
- Read branch and pull request context.
- Create branches and pull requests.
- Read and post Azure Repos pull request comments.
- Read and post Azure Boards work item comments.

OpenHands does not require users to paste a personal access token for Azure
DevOps repository access when Microsoft Entra sign-in is configured.

## Respond to @openhands Comments

OpenHands can respond when someone mentions `@openhands` in an Azure Repos pull
request comment or an Azure Boards work item comment. Service hooks are
installed per organization:

1. In the OpenHands web app, go to **Settings** > **Integrations**. The
   **Azure DevOps webhooks** section lists each Azure DevOps organization you
   belong to.
2. Select **Install** for each organization that should respond to mentions.

The person installing needs the OpenHands permission to manage integrations
and the Azure DevOps permission to create service hooks in that organization.
OpenHands reads the organization from each event, checks that the commenter
has write access to the repository in that organization, and replies in the
same pull request or work item. The commenter needs an OpenHands account.

## Trigger OpenHands from Azure DevOps

Azure DevOps events can be connected to OpenHands automations through Azure
DevOps Service Hooks and OpenHands custom webhooks. Use this pattern for
workflows such as:

- A work item comment that asks OpenHands to create an implementation pull
  request.
- A pull request comment that asks OpenHands to review the change.
- A pull request comment that asks OpenHands to generate tests or validation
  evidence.
- A pipeline or incident event that asks OpenHands to inspect logs and propose a
  fix.

To configure this pattern:

1. Register a custom webhook in OpenHands. See
   [Event-Based Automations](/openhands/usage/automations/event-automations#custom-webhooks).
2. Create an Azure DevOps Service Hook that sends the selected event to the
   webhook URL.
3. Create an OpenHands automation that filters for the event type, repository,
   project, or trigger phrase you want to support.
4. Test with a non-production repository or project before enabling the
   automation broadly.

<Note>
  GitHub has built-in event routing in OpenHands. Azure DevOps event routing is
  configured through service hooks or custom webhooks.
</Note>

## Troubleshooting

| Symptom | Check |
| --- | --- |
| The Azure DevOps login option is not visible | Confirm **Azure DevOps Authentication** is enabled in the Admin Console or Helm values and the deployment has been applied. |
| OAuth redirects fail | Confirm the Entra redirect URI exactly matches `https://<your-auth-hostname>/realms/allhands/broker/azure_devops/endpoint`. |
| Microsoft sign-in shows an invalid client or secret error | Confirm the Azure DevOps Client ID and Client Secret match the Microsoft Entra app registration. If the secret expired, create a new one and redeploy. |
| Microsoft sign-in succeeds but no repositories are listed | Confirm the user is a member of the Azure DevOps organization and has access to its projects and repositories. |
| `@openhands` comments in an organization get no response | Confirm that organization shows **Installed** under **Azure DevOps webhooks** in **Settings** > **Integrations**, and that the commenter has an OpenHands account and write access to the repository. |
| Consent fails or Azure DevOps API calls are denied | Confirm the Entra application has the required Azure DevOps delegated permission and that admin consent has been granted if your tenant requires it. |
| Repository selection or Git operations fail | Confirm OpenHands can reach `dev.azure.com` and that the repository is referenced as `organization/project/repository`. |
| OAuth V2: Microsoft shows `AADSTS650057` | The provider's **Scopes** include `499b84ac-1321-427f-aa17-267ca6975798/.default`. Use the named scopes from [Configure the Auth Provider](#configure-the-auth-provider), or add the Azure DevOps API permission to the app registration. |
| OAuth V2: Microsoft says the redirect URI doesn't match | Add the **Redirect URL** from the provider page in **Auth Providers** to the Entra app registration's Web redirect URIs. |
| OAuth V2: Azure DevOps stops working after the access token expires | Confirm the provider's **Scopes** include `offline_access`. Then reconnect Azure DevOps in **Settings** > **Integrations** so OpenHands receives a refresh token. |
| Azure DevOps Service Hook deliveries do not trigger an automation | Confirm the custom webhook is registered, the Service Hook URL is correct, the event type matches the automation, and the automation is enabled. |
